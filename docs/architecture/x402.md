# x402 Support

Saksi implements an x402-compatible exact-payment flow for Stellar classic assets. It is intentionally scoped and not yet the published Soroban/SEP-41 v2 scheme.

## Flow

1. `POST /v1/x402/risk-report` with `{ "invoiceId": "<64 hex>" }`.
2. Without `x-payment`, the API returns HTTP 402 with `accepts[0]`:
   - `x402Version: 1`
   - `scheme: "exact"`
   - `network: "stellar:testnet"` or `stellar:pubnet`
   - `maxAmountRequired`: atomic units as a string
   - `asset`: `native` or `CODE:ISSUER`
   - `payTo`, `resource`, `maxTimeoutSeconds`
   - `extra.memo`: `saksi:` + first 22 hex chars of SHA-256(invoiceId)
   - `extra.invoiceId`
3. Client pays on Stellar with the memo and sends `x-payment: base64({ "txHash": "<64 hex>" })`.
4. Verifier checks Horizon: successful transaction, memo match, age within `maxTimeoutSeconds`, payment to `payTo`, asset match, amount at least `maxAmountRequired` (atomic).
5. Replay store claims the lowercase tx hash. `FileReplayStore` uses atomic file creation; `InMemoryReplayStore` is for tests.

## Environment

- `SAKSI_X402_PAY_TO` — destination account (enables x402 when set with asset)
- `SAKSI_X402_ASSET` — `native` or `CODE:ISSUER`
- `SAKSI_X402_NETWORK` — default `stellar:testnet`
- `SAKSI_X402_AMOUNT` — atomic units, default `10000000`
- `SAKSI_X402_RESOURCE` — absolute resource URL
- `SAKSI_X402_HORIZON_URL` — default testnet Horizon
- `SAKSI_X402_MAX_TIMEOUT_SECONDS` — default 60
- `SAKSI_X402_REPLAY_DIR` — default `.data/x402-replay`

## Limitations

- Classic assets only; Soroban SEP-41 v2 is not implemented.
- Overpayment is accepted; there is no refund logic.
- `FileReplayStore` is single-host and not a distributed lock. Use Postgres or Redis for multi-replica deployments.
- Proof is a minimal `{ txHash }` payload, not the full standard `PaymentPayload`.
- Do not claim full x402 v2 interoperability until the standard payload and Soroban asset scheme are implemented.
